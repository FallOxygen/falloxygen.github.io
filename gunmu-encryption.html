解码规则

  1. 搜索帧头 U+2060 U+2060；逐个候选位置尝试，因此混在普通文字中的隐形文本也能被提取。
  2. 帧头之后连续读取 U+200C(=0) / U+200D(=1)，直到帧尾 U+2060 或任何其他字符。
  3. 比特数必须 ≥ 16 且为 8 的整数倍，否则判定为被截断。
  4. 末 2 字节为 CRC-16（CCITT-FALSE，poly 0x1021，init 0xFFFF）校验和，不符即判定内容被改动。
  5. 其余字节以严格模式（TextDecoder fatal）还原为 UTF-8 文本，失败即判定载荷损坏。
  6. 任何一步失败，统一报告「不是有效的隐形编码文本」并附具体原因。

边界情况

  • 空字符串：友好提示「结果为空」，不报错。
  • 孤立代理项（U+D800–U+DFFF 未配对）：UTF-8 会将其替换为 U+FFFD，不可逆 → 编码时拒绝并说明。
  • 被平台截断：比特数不再是整字节 → 解码立即报错。
  • 字符被替换 / 删除：CRC-16 + UTF-8 严格校验双重检出；校验仅为完整性设计，不提供密码学强度。
  • Unicode 规范化：部分平台会自动合成/分解组合字符（如 é = e + ́），解码结果可能为视觉等价的另一种形式。
  • 紧邻 Emoji：ZWJ（比特 1）若贴近 Emoji 可能被渲染引擎并入 Emoji 序列；帧头尾 U+2060 已在载荷两侧隔离，建议隐形文本独立成段。

防格式化建议：① 隐形文本尽量独立传输，避免进入富文本管道；② 必须混排时放在引号或括号等可见锚点之间； ③ 粘贴到解码区后先看「字符组成检查」—— 若 U+200C / U+200D 计数为 0，说明已被平台剥离。
哪些输入会解码失败：被平台剥离或截断的文本、手工编辑过的隐形字符、编码时含孤立代理项的原文（会被直接拒绝）、经过 NFC/NFD 规范化后字节已改变的文本（可能解出规范化变体）。

05 · SECURITY NOTICE

安全说明（请务必阅读）

隐写 / 编码 ≠ 加密
  • 本方案更准确的定位是隐写（steganography）/ 编码，而不是高强度加密：它隐藏的是内容的存在，而不是内容的可读性。
  • 方案没有密钥参与。任何知道算法规则的人拿到隐形文本都可以完整还原 —— 请勿用它保护真正敏感的信息。
  • 若需要真正的保密性，推荐叠加标准加密：明文 → AES-GCM（由密码经 PBKDF2 派生密钥）→ 密文字节 → 本算法隐形化。此时攻击者即使提取出隐形字符，得到的也只是密文。
  • 若实现密码模式：密码只在浏览器本地参与密钥派生与解密，绝不上传任何服务器。本页同样为纯前端实现，所有处理均在本地完成。
// 密码模式扩展草图（Web Crypto，全部本地执行）：
const salt = crypto.getRandomValues(new Uint8Array(16));
const iv   = crypto.getRandomValues(new Uint8Array(12));
const base = await crypto.subtle.importKey('raw', new TextEncoder().encode(password), 'PBKDF2');
const key  = await crypto.subtle.deriveKey(
  { name:'PBKDF2', salt, iterations:310000, hash:'SHA-256' },
  base, { name:'AES-GCM', length:256 }, false, ['encrypt']);
const ct   = await crypto.subtle.encrypt({ name:'AES-GCM', iv }, key, plainBytes);
// 将 salt | iv | ct 拼接后用本算法编码为隐形字符；解码端输入密码逆向还原
